<h1 align="center">Projects Emergence</h1>

<p align="center"><strong>用研究构建知识的方式，构建项目。</strong></p>

<p align="center">一个将学术研究方法应用于项目和产品开发的 Agent Skill。</p>

<p align="center"><a href="README.md">English</a></p>

## 核心思想

Projects Emergence 不把项目理解为一组等待完成的任务，而把它理解为一串可以检查、验证和修正的决策。

学术研究已经形成了一套处理不确定性的方法：提出研究问题、考察相关工作、复现关键结果、建立可证伪假设、设计实验、评估证据、暴露局限并修正结论。Projects Emergence 将这套逻辑迁移到项目和产品开发中。

它**不是**把每个项目变成论文，也不是把每个任务变成完整调研。它提取使知识更可信的机制，并根据当前决策的重要性和不确定性按比例使用。

## 从学术研究到项目与产品

| 学术研究 | 项目与产品开发 |
|---|---|
| 研究问题 | 用户问题与项目目标 |
| 文献综述 | 现有产品、论文、仓库与案例调研 |
| 复现实验 | 复现参考方案的关键机制或可观察行为 |
| 研究假设 | 产品假设或改进假设 |
| 实验设计 | 能够检验假设的最小实现 |
| 实验结果 | 测试、日志、对照与用户证据 |
| 讨论与局限 | 反思、质疑与尚未证实的结论 |
| 修订 | 重新进入调研并修正项目 |
| 发表 | 可复现、可审查的公开交付 |

一个粗糙想法只有形成可追溯的推理链，才真正成为项目：

~~~text
研究问题
  → 相关工作
  → 关键复现
  → 提出假设
  → 最小实验
  → 获得证据
  → 反思
  → 修正或发布
~~~

在 Agent 工作流中，它表现为一个实用的决策循环：

~~~text
澄清 → 调研 → 复现或适配 → 实现
     → 反思 → 调研 → 修正
~~~

## 底层原则

### 调研必须服务于决策

调研不是项目开始前的仪式。每轮调研都必须回答：

1. 为什么现在需要查？
2. 查到什么程度就足够？
3. 这些证据将支持哪个具体决定或动作？

调研深度应与决策的不确定性和后果相匹配。新的产品方向可能需要完整比较；需求明确、风险很低的机械修改则可能只需要直接实现和验证。

### 把已有方案视为相关工作

目标不是强行制造创新。已有产品和项目是需要理解其机制、边界与许可证的相关工作。

- **复现**：成熟方案已经满足目标。
- **适配**：机制有效，但用户、设备、风格或工作流不同。
- **改进**：证据揭示了一个具体缺陷。
- **重新设计**：已有方案无法满足核心要求。

复现不是失败；没有证据支持却重新发明一次，才是问题。

### 在投入之前通过证据闸门

进入大规模实现前，Skill 会回放问题定义、相关工作、当前证据、最强的不确定性、准备执行的最小实验，以及公开与私有信息的边界。

研究闸门阻止 Agent 在用户尚未接受问题定义和实现范围时，把一个有吸引力的想法直接扩张成大型实现。它既是证据检查点，也是用户决策权的边界。

### 把实现视为实验

第一版实现不是“能够发布的最小功能”，而是**能够提供信息的最小切片**。

它的任务是检验当前假设，并让我们能够明确区分：复现了什么、改变了什么、观察到了什么证据，以及仍然不知道什么。

### 把反思视为纠错机制

代码能够运行，不代表项目已经成立。反思需要追问：它是否解决了原始问题，是否真的优于直接使用参考方案，以及哪一项结论仍然脆弱。

当反思暴露出关键问题，项目会带着一个更窄的新问题重新进入调研。这个循环是递归的，因为新的认识会改变项目本身。

### 把发布视为有边界的主张

公开成果只能陈述证据能够支持的内容。外部工作需要归因，局限需要保留，尚未验证的假设不能被包装成已经证明的结果。

公开成果负责让项目容易理解，代码仓库负责让项目可以复现，私人工作记录则可以保留更完整的过程。

## 一个简短示例

假设最初的想法是：“做一个本地优先的阅读工具。”

1. **研究问题**：现有工具尚未解决的是哪个具体阅读问题？
2. **相关工作**：比较代表性产品，并理解本地存储、标注和检索背后的机制。
3. **关键复现**：先复现核心行为，而不是立刻开发完整应用。
4. **提出假设**：某项具体的工作流改变，可以降低特定用户在特定场景中的阻力。
5. **最小实验**：只实现验证这项主张所需的部分。
6. **获得证据**：比较行为、收集用户反馈或检查相关指标。
7. **反思**：决定继续、修正、直接复用现有方案，或者停止。
8. **发布**：说明证明了什么、借鉴了什么、还不知道什么。

最终产物不只是更多代码，而是一个其决策过程和公开结论都能够被检查与修正的项目。

## Beta 内容

- 针对新想法、设计选择、Bug 和发布风险选择合适的调研深度。
- 在大规模实现前设置证据与用户确认闸门。
- 明确区分复现、适配、改进和重新设计。
- 先实现能够验证假设的最小信息切片，再扩大范围。
- 根据产品、工具、研究、创意或数据项目选择反思问题。
- 提供可选的调研、反思和公开项目元数据模板。
- 提供可选的作品集、多项目和 Git worktree 协作模式。
- 包含 skills-only Codex plugin manifest。

## 安装

可以让 Codex 直接从 GitHub 安装：

~~~text
$skill-installer 从 https://github.com/xlth10/projects-emergence/tree/main/skills/projects-emergence 安装 projects-emergence
~~~

也可以手动克隆并把 Skill 复制或链接到 `~/.agents/skills/`：

~~~bash
git clone https://github.com/xlth10/projects-emergence.git
mkdir -p ~/.agents/skills
ln -s "$(pwd)/projects-emergence/skills/projects-emergence" ~/.agents/skills/projects-emergence
~~~

如果没有立即出现，请重启 Codex。

## 使用

显式调用：

~~~text
$projects-emergence 我有一个灵感：做一个本地优先的阅读工具。
~~~

也可以直接描述符合范围的任务。Skill 默认允许自动匹配。

## 设计边界

Beta 版本不会：

- 要求每个任务都编写学术式文档；
- 把每个实现问题都升级成完整调研；
- 在复现或适配更诚实时强制追求创新；
- 强制依赖 Notion 或其他知识库；
- 包含用户本地路径、私人项目编号或内部记录；
- 未经授权自动提交、推送、部署、购买或发送消息；
- 因为代码能够运行就自动宣称项目已经完成。
